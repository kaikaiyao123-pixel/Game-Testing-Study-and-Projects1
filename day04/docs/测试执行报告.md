## 四、问题清单：位置与最小修改方案

### P0-1　游标分页 off-by-one，每翻一页丢 1 条（真实实现缺陷，§9 口径①）

- **位置**
  - `backend/src/main/java/com/example/blog/service/MomentService.java:48-49`（生成 `nextCursor`）
  - `backend/src/main/java/com/example/blog/repository/MomentRepository.java:74`（下一页严格 `<` 过滤）
- **现象（确定性证据）**
  - 实验 A：插 12 条、size=5、翻 3 页，只收集到 10 条，遗漏 `#5 (b3e4edc7)` 与 `#11 (db77111a)`。
  - 实验 B：插 20 条、size=8、翻 3 页，只收集到 18 条，遗漏 2 条。
  - 两次遗漏项**恰为每页 `nextCursor` 指向的那一条**，与理论推演逐条吻合；无重复、createdAtMs 单调递减。
- **根因**
  - `MomentRepository.timeline` 取 `LIMIT size+1`（多取 1 条判 `hasMore`）。
  - `MomentService.timeline:48` 用 `items.get(size)`（多取的第 size+1 条）生成 `nextCursor`。
  - `CursorPage.of` 只把 `items[0..size-1]` 返回客户端，**那条多取记录本页不返回**。
  - 下一页 SQL 为严格 `created_at_ms < ? OR (= AND id < ?)`，**又把游标本身排除**。
  - 结果：该记录既不在本页、也不在下一页，永久跳过；每翻页丢 1 条。
- **最小修改方案（改 1 行 + 注释，其余全部不动）**
  ```java
  // MomentService.java:48  原
  Map<String, Object> last = items.get(size); // 多取的那一条，用于生成下一页游标

  // 改为（本页最后一条「已返回给客户端」的记录）
  Map<String, Object> last = items.get(size - 1);
  ```
  `nextCursor` 编码、`CursorPage.of`、`MomentRepository` 的严格 `<` 均保持不变。改后：页1 游标指向 `#4` → 页2 `< #4` 从 `#5` 开始 → 不重不漏。`hasMore = items.size() > size` 判定仍成立。
- **影响范围**：仅 `GET /api/moments` 时间线（全项目唯一使用 `CursorCodec`/`CursorPage` 的游标分页；其余列表走 `PageQuery` 偏移分页，不受影响）。
- **必须同步补的断言**：把本次补测的多页断言（插 N 条 → 翻页收集 → 断言数量相等 + 无重复 + 时间单调）固化进 `verify-p3.js` 的 `testMoments`，否则该缺陷会再次「脚本全绿」地漏过。

### P1-1　`p3_smoke_test.sh` 假绿（脚本缺陷）

- **位置**：`tools/p3_smoke_test.sh:10`（手机号生成）、以及所有 `ok()` 判等（如 `:15`、`:22`、`:54`）。
- **现象**：`PHONE="1380013$(printf '%04d' $RANDOM)"` 生成 **12 位**手机号（`138001319540`），被后端 `^1[3-9]\d{9}$` 正确拒绝（400），`FAIL: register`。注册失败后 `TOKEN1/TOKEN2` 为空，而判等语句为 `echo "$X" | grep -q "$TOKEN"` —— **空串模式 `grep -q ""` 恒匹配**，于是 media/collection/moment/share 的 6 个「PASS」全是假阳性；实际登录态接口全返回 401/404。
- **最小修改方案**
  1. 手机号改为 11 位合法：`PHONE="138$(printf '%08d' $((RANDOM % 100000000)))"`。
  2. `ok()` 判等增加非空守卫，例如 `[ -n "$TOKEN1" ] && echo "$L1" | grep -q '"ok":true'`；所有依赖 token/id 的判等都要求变量非空，禁止用空串做 grep 模式。

### P1-2　`verify-stack.js` 空库假设导致假失败（脚本缺陷，非后端缺陷）

- **位置**：`tools/verify-stack.js:228-229`，硬编码 `finalHealth.body.userCount === 0`。
- **现象**：库内存在 2 个既有账号时得 35/36；探针自建账号已正确清理（「测试账号已从 MySQL 清理」PASS），失败纯粹是「回到初始状态」被写成「回到 0」。
- **最小修改方案**：脚本开场先取 `initialUserCount`（`GET /api/health`），末尾断言 `userCount === initialUserCount`，而非 `=== 0`。或按测试计划 §1.3 走「备份 → 清空 → 跑 → 恢复」。前者改动更小且不触碰数据。

### P1-3　`verify-p3.js` / `verify-p3-ui.js` 断言缺口（脚本缺陷）

- **位置**：`tools/verify-p3.js:83-84`（注释明写「无第二账号时跳过」，仅验证 owner 自读 200）、`:106-114`（改密只验旧密码 401 / 新密码 200）；`tools/verify-p3-ui.js`（无 noindex 断言）。
- **现象**：§5.1 / 5.2 / 5.3 / 5.6 / 5.7 / 5.8 六类口径未被自动证伪；其中 5.6 恰好掩盖了 P0-1。
- **最小修改方案**：将本次补测探针（`%LOCALAPPDATA%\Temp\blogg_p3_gap_probe.js`）中的 5.1 / 5.2 / 5.3 / 5.6 / 5.7 断言合并进 `verify-p3.js`（用第二账号 + Redis TTL 查询）；`verify-p3-ui.js` 的 `share.html` 静态校验加 `html.includes('noindex')`。**优先级最高的是 5.6 多页断言**。

### P2-1　外链失效探测「只标记不删」功能未接线（比「未测」更严重）

- **位置**：`MediaRepository.java:149`（`dueForLinkCheck`）、`:156`（`updateLinkCheck`）；`CollectionItemRepository.java:118`、`:127`。
- **现象**：全后端 `grep` 确认这两个方法**只有定义、零调用方**；无 `@Scheduled`、无 `@EnableScheduling`、无任何端点、无 `HttpClient`/`RestTemplate`/`WebClient`/`openConnection`。`link_status` 仅在创建时置 `unchecked` 或由 `PATCH /api/media/{id}/status` 手工改写，探测逻辑（低频 + 退避 + 只标记不删）**未实现**。`docs/P3实施与验收方案.md:73`（W1⑥）、`:82`（W2⑤）承诺了该能力。
- **最小修改方案（二选一）**
  - 实现：新增一个 `@Scheduled(fixedDelay=…)` 的 `LinkCheckService`，批量取 `dueForLinkCheck(now, limit)` → 对外链发 HEAD/GET → 调 `updateLinkCheck(id, status, checkedAt, recheckAfter, failCount)`（含指数退避），并在 `BlogApplication` 加 `@EnableScheduling`；勿删记录、勿自动跳转。
  - 或如实降级：在 P3 方案与 README 标注该能力为「数据结构预留、P3 不实现」，移除验收口径中的相关表述。
  - 任一方案落地后，再补「手工置 `invalid` → 触发探测 → 断言行仍在且仅状态字段变化」的自动断言。

### P2-2　`p0-baseline.json` 元数据语义失真（文档/数据问题，不影响验收）

- **位置**：`tools/p0-baseline.json`（`note`、`p0Snapshot`、`p3Modified`）；`tools/p0-probe.js:9` 注释。
- **现象**：`p0Snapshot` 与 `files` 的 57 个 SHA256 **完全相同**（`p0Snapshot` vs `files` 差异数 = 0），所有 `p1Modified`/`p2Modified`/`p3Modified` 登记的文件都是「登记但无差异」；`p3Modified` 仅 `["README.md"]`。文档声称「P0 精确零改动快照归档在 `p0Snapshot` 供追溯」，实际已无法追溯任何阶段改动。`p0-probe` 第 1 节只比对 `baseline.files`，故 S3 仍 54/54 通过——**这是元数据的可追溯性退化，不是功能缺陷**。
- **最小修改方案**：将 `note` 与 `p0-probe.js:9` 注释改为如实描述「`p0Snapshot` 为刷新后的连续性快照」，或回填真实的 P0 原始哈希并按实际改动补全 `p3Modified` 列表。无需改动任何判定逻辑。
