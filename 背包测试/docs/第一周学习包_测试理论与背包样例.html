Day 1 · 等价类划分与边界值分析

1.1 为什么需要设计方法

凭感觉测背包，你会做的动作大概是：打开背包、看看道具、用一个、丢一个。约 10 个动作。但背包的状态组合远不止 10 个：容量从 0 到 200、道具从普通到限时到锁定、操作从使用到拆分到批量整理、再叠加断网与多端。

方法的价值不是让测试变复杂，而是让遗漏变得可见。没有方法，你不知道自己漏了什么；有了方法，你能算出「应该有多少条、现在有多少条」。

1.2 等价类划分：三步

  1. 识别所有输入项（购买数量、道具 ID、名称文本、剩余次数）
  2. 为每个输入划分有效等价类——程序应该正常处理的值
  3. 为每个输入划分无效等价类——程序应该拦截的值

同一个类里任取一个值即可，因为它们对程序的作用等价。这一步把「无穷多输入」压缩成「有限几类」。

1.3 边界值：三个点

缺陷集中在边界，因为边界是比较条件写错的地方。对每个边界取三点：

  • 上点：边界本身的值（200）
  • 内点：边界内侧最近的有效值（199）
  • 离点：刚越过边界的无效值（201）
游戏测试的关键差异：边界不只是输入框，状态本身也有边界。背包容量 200、道具剩余次数 0、金币 0、等级上限、堆叠上限、时间 23:59:59——这些都属于边界值分析。只盯着输入框，会漏掉游戏里最核心的一批缺陷。

Day 2 · 判定表、状态迁移、场景法

2.1 三种方法解决三类不同问题

方法解决什么识别信号
判定表多个条件共同决定一个动作需求里出现「且」「或」「如果…同时…」
状态迁移状态之间的流转与非法流转功能有「待处理 / 进行中 / 已完成」这类状态词
场景法端到端链路是否走得通要串起多个模块才能完成一件事

2.2 样例 A：整理规则的判定表

「整理」按钮的规则受三个条件影响：背包是否有空格、是否存在可堆叠道具、是否存在锁定道具。三个条件各两个取值，共 8 条规则：

规则有空格可堆叠有锁定预期动作
R1是否否按默认顺序紧凑排列
R2是否是排列，锁定格位保留
R3是是否先合并同类，再紧凑排列
R4是是是合并同类，锁定道具不参与合并与移动
R5否否否无可整理内容，提示或按钮置灰
R6否否是无可整理内容，锁定道具保持原位
R7否是否仅执行合并，合并后腾出空格
R8否是是合并非锁定道具，锁定道具不动
这张表真正的用途不只是设计用例。R4 和 R8 里「锁定道具是否参与合并」如果策划案没写，你就要在需求评审时提出来。判定表能暴露需求文档的空白——这比事后提 Bug 有价值得多。

道具的六个状态：未获得 · 持有 · 使用中 · 已消耗 · 已锁定 · 已过期。下表每个 ✗ 都是一条必测用例：

起始 \ 事件拾取使用锁定解锁到期丢弃
未获得持有✗✗✗✗✗
持有✗使用中已锁定✗已过期未获得
使用中✗✗✗✗✗✗
已消耗✗✗✗✗✗✗
已锁定✗✗✗持有已过期✗

36 个格子里合法迁移只有 9 条，其余 27 条非法迁移才是缺陷最密集的区域。已消耗的道具能否再次使用、已过期的能否生效、已锁定的能否被批量丢弃——这些路径如果服务端没做状态校验，就会出现刷取资源的严重问题。

2.4 样例 C：拾取链路的场景法

场景路径验证重点
基本流击杀 → 掉落 → 拾取 → 入包 → 刷新显示链路走通，数量与 ID 正确
备选 1拾取时背包已满提示明确，掉落物保留在地面
备选 2拾取瞬间断网重连后状态一致，不吞不重
备选 3拾取成功但响应丢失有查询补偿，不重复拾取
备选 4拾取响应重复推送幂等，只入包一次
备选 5拾取过程中切后台返回后进度与数据一致
备选 6多端同时拾取同一掉落仅一次成功，另一端收到刷新

基本流跑通一次就够；备选流承担这条链路绝大部分的测试价值，每一条都可能对应一次线上问题。

Day 3 · 用例规范与 12 条完整样例

3.1 一条用例的八个要素

编号、所属模块、用例标题、前置条件、操作步骤、预期结果、设计方法、优先级。

其中设计方法是新人最常省、但面试最常问的一列。它能回答「这条用例怎么来的」。写不出这一列，说明是拍脑袋想的。

3.2 唯一的判断标准

把用例交给一个完全不了解背景的人，他能不能不追问、直接照着执行并判断通过与否？能，就是合格的；不能，就缺了东西。前置条件没写、步骤合并了多个动作、预期结果写成「正常」，都属于不合格。

3.3 好坏对照

不合格合格
测试背包满了会怎样A04 背包 200 格满时拾取第 201 个
步骤：打开背包，测试一下1. 进入副本击杀怪物产生掉落
2. 点击拾取
3. 观察提示与背包状态
预期：正常提示「背包已满」；掉落物保留在地面；背包数量仍为 200

3.4 十二条完整样例

下面 12 条覆盖五种方法与六个模块，作为书写格式的基准。先自己写 10 条，再对照这里找差距。

A04 ｜ 背包 200 格满时拾取第 201 个 （边界值·上点 · P0）
前置条件
账号已登录；背包容量上限 200；背包已放入 200 个不堆叠的道具
操作步骤
1. 进入副本并击杀怪物，掉落 1 个道具
2. 点击拾取
3. 观察提示与背包状态
预期结果
提示「背包已满」；掉落物保留在地面不被吞掉；背包道具数量仍为 200；服务端下发拒绝且客户端不显示新增
设计说明
这是上点用例。若只测 199 不测 200，满包逻辑的错误就会被漏掉。需同时检查掉落物是否还在，否则会出现「吞道具」。
A16 ｜ 拾取过程中断网 （场景法·异常 · P0）
前置条件
背包 100 格；网络正常；可在弱网工具中模拟断网
操作步骤
1. 击杀怪物产生掉落
2. 点击拾取的瞬间断开网络
3. 恢复网络并等待重连
4. 查看背包与地面
预期结果
重连后状态一致：要么拾取成功且道具在背包，要么拾取失败且道具仍在地面；不得出现两端都扣或两端都在的情况
设计说明
断网类用例的预期结果往往不是单一值，而是「一致性约束」。这类写法是游戏测试与普通软件测试的重要差别。
B03 ｜ 使用剩余次数为 0 的道具 （边界值·零点 · P1）
前置条件
持有一个多次使用道具，剩余次数已被消耗至 0，且道具未从背包消失
操作步骤
1. 打开背包找到该道具
2. 点击使用
3. 观察响应
预期结果
不可使用；界面置灰或提示次数已用尽；不触发任何效果；服务端不产生消耗记录
设计说明
零点边界容易触发除零、空指针或「负数次数」。要同时验证客户端不响应与服务端不记账。
B13 ｜ 批量丢弃中混有锁定道具 （判定表 · P0）
前置条件
背包中有 3 个道具，其中第 2 个已锁定；支持多选批量丢弃
操作步骤
1. 进入批量选择模式
2. 全选 3 个道具
3. 点击丢弃并确认
4. 查看背包
预期结果
仅未锁定的 2 个被丢弃；锁定道具保留且仍处于锁定状态；给出「已跳过锁定道具」的明确提示
设计说明
判定表里的组合场景。若实现为「全成功或全失败」，都会产生错误结果，必须验证部分成功的处理。
C08 ｜ 已过期 → 使用中（非法使用） （状态迁移·非法 · P0）
前置条件
持有一个限时道具；通过修改服务器时间或等待使其到达过期时刻
操作步骤
1. 不重进游戏，停留在背包界面直至道具过期
2. 直接点击该道具的使用按钮
3. 观察结果
预期结果
使用被拒绝；提示道具已过期；不产生任何效果；道具随后被清理或标记为过期
设计说明
非法迁移必须通过多端、界面未刷新、时间篡改等方式主动构造。不能因为「正常玩家不会这样」而跳过。
C10 ｜ 跨天 00:00:00 限时道具到期 （边界值·时间 · P0）
前置条件
限时道具将在当日 23:59:59 后到期；服务器时间可控或可等待
操作步骤
1. 在 23:59:58 查看倒计时
2. 等到 00:00:00
3. 观察道具状态与倒计时显示
预期结果
道具在 00:00:00 准时失效；倒计时不出现 -1 秒或 00:00:00 仍可使用；跨天任务同步刷新
设计说明
时间边界是游戏测试特有的高频缺陷区。必须区分服务器时间与本地时间，后者可被玩家修改。
C15 ｜ 多端同时登录操作同一道具 （场景法 · P0）
前置条件
同一账号在设备 A 与设备 B 同时在线；背包中有 1 个消耗品
操作步骤
1. 设备 A 与 B 同时打开背包
2. 两端几乎同时使用同一道具
3. 查看两端显示与服务端记录
预期结果
仅一次生效；另一端收到状态刷新；道具只扣 1 个；不出现重复发放效果或负数
设计说明
涉及并发与幂等，属于资金与资源安全类问题，一律按 P0 处理。
D04 ｜ 有空格 + 有可堆叠 + 有锁定时整理 （判定表 R4 · P0）
前置条件
背包中存在空格、两堆可合并的同类道具、以及至少 1 个锁定道具
操作步骤
1. 记录整理前所有道具的 ID、数量与锁定状态
2. 点击「整理」
3. 等待动画结束并核对
预期结果
同类道具正确合并；锁定道具位置保持不变或按规则保留；整理前后道具 ID 与总数量完全一致
设计说明
三种条件同时满足是组合最复杂的一条规则。验证要点是「数据不变」而非「看起来整齐」。
E09 ｜ 使用回调重复推送 （场景法·幂等 · P0）
前置条件
可在测试环境重放服务端回调，或通过抓包工具重复发送同一响应
操作步骤
1. 使用 1 个道具并捕获成功响应
2. 将该响应重复推送 3 次
3. 查看道具数量与效果记录
预期结果
效果只结算一次；道具只扣 1 个；服务端有幂等键或去重记录；不产生重复日志告警以外的副作用
设计说明
幂等是支付与资源类链路的核心。重复回调在真实网络环境中必然发生，不是理论假设。
E12 ｜ 热更新后背包数据兼容 （场景法 · P0）
前置条件
存在一份热更新前产生的存档；准备新版本配置
操作步骤
1. 用旧版本账号产生背包数据
2. 执行热更新到新版本
3. 打开背包并使用道具
预期结果
旧道具可正常显示与使用；新增字段有默认值；不出现解析失败、闪退或道具丢失
设计说明
热更新是游戏特有的发布方式。老数据与新配置的兼容性必须在版本切换时验证。
F05 ｜ 连续开关背包 50 次内存增长 （性能 · P1）
前置条件
中端机型；已接入性能采集工具；背包内有 150 个道具
操作步骤
1. 记录初始内存
2. 连续打开、关闭背包 50 次
3. 记录结束内存并等待 GC
4. 观察帧率曲线
预期结果
结束内存较初始值增长在可接受阈值内且可回收；过程中无持续掉帧；不出现 OOM 崩溃
设计说明
性能用例的预期结果必须给出可量化的判定，只写「不卡」无法验收。阈值需与项目标准对齐。
F09 ｜ 道具名称含特殊字符 （等价类·无效 · P1）
前置条件
具备可自定义道具名称的能力（如装备命名、礼包自定义字段）
操作步骤
1. 输入含 % 、' 、; 、尖括号与 emoji 的名称
2. 保存
3. 在背包、交易行、排行榜三处查看
预期结果
正确保存并原样显示；不截断界面；不引发注入或脚本执行；三处显示一致
设计说明
特殊字符不只是「能否输入」，还要验证跨模块显示与安全性，这是等价类里最常被跳过的一类。

Day 4 · 缺陷管理与 5 条 Bug 单样例

4.1 生命周期

新建 → 已指派 → 修复中 → 待验证 → 已关闭。三个分支：重新打开、拒绝（不修 / 无法复现 / 设计如此 / 重复）、延期（务必记录影响版本号）。

4.2 严重程度与优先级不是一回事

维度严重程度 Severity优先级 Priority
定义缺陷对系统的破坏力修复的紧急程度
判定者测试人员（技术判断）产品或主程（商业判断）
依据功能失效程度、数据影响影响用户量、上线时间、修复成本

高严重 + 低优先级是真实存在的。资源有限时按「影响用户量 ÷ 修复成本」排序，不是按破坏力排序。能说清这一点，说明你理解项目运作。

4.3 五条完整 Bug 单

Day 5 · 游戏架构常识

这一天的目的不是学开发，而是知道数据存在哪、谁做校验、什么情况下会出现你正在测的那些 bug。

5.1 客户端与服务端各存什么

位置通常存什么测试含义
客户端界面、图标、动画、本地缓存的配置表显示错误多为客户端问题
服务端道具数量、金币、订单、任务状态等权威数据数据错误一定是服务端或同步问题
配置表道具 ID、堆叠上限、价格、掉落概率数值类缺陷先查配置，再查代码
判断口诀：「界面显示错、数量对」→ 客户端；「数量错、账变」→ 服务端；「重登后恢复」→ 客户端缓存；「重登后仍错」→ 服务端数据。这条判断能力，靠的就是 Day 5 的内容。

5.2 一次「使用道具」背后发生了什么

  1. 客户端点击 → 做一次本地预检查（等级、冷却、数量），决定按钮是否可点
  2. 发送请求到服务端，带上道具 ID 与操作类型
  3. 服务端重新做一遍完整校验（不能信任客户端）
  4. 服务端写数据库，扣道具、发效果、记流水
  5. 服务端下发结果，客户端更新界面

第 3 步是关键。如果开发者只在客户端做了校验、服务端省略了，那么通过抓包改请求、多端并发、界面未刷新等手段就能绕过限制——这正是 C08、C15、E09 这几条用例能测出问题的原因。

5.3 帧循环、状态同步与热更新

  • 帧循环：客户端按帧刷新，所以「界面未刷新时仍能操作」是真实可构造的场景，不是假想
  • 状态同步：服务端是权威，客户端只是投影。断线重连后应以服务端为准，这决定了 C14 的预期结果写法
  • 热更新：不发安装包即可更新配置与逻辑，所以老存档必须能兼容新版本（E12、E13）
  • SDK：渠道登录、支付、实名认证、防沉迷，各自是独立链路，容易出现「游戏逻辑没问题但支付回调异常」

5.4 样例：一次「道具消失」缺陷的定位过程

现象：玩家反馈背包里少了一个道具，无操作记录
第 1 步
重登游戏 → 道具仍未出现，排除客户端缓存问题
第 2 步
查服务端道具流水 → 存在一条「使用消耗」记录，但玩家否认使用
第 3 步
查该时间点的请求日志 → 发现两条相同请求，间隔 180ms
第 4 步
抓包复现 → 弱网下快速双击可稳定触发两次请求
第 5 步
查服务端代码 → 使用接口无幂等键，两次请求各扣一次道具
结论
服务端幂等缺失，非客户端问题；对应本包 BUG-03 与用例 E09、C15

这个过程说明了一件事：不懂架构也能提 Bug，但只能写「道具不见了」；懂架构才能把缺陷定位到具体环节，让开发十分钟就能修。这是初级与中级测试的分水岭。
